# 收工

固定顺序：**定范围 → 跑测试 → 审阅 → 扫描 → 摘要**。

流程、扫描边界、测试记录和摘要格式由本 Skill 固定；具体测试选择、代码含义、结果是否合理以及失败原因，由 AI 结合项目上下文判断。追求相同的执行标准，不承诺不同 AI 得出完全相同的解释。

## 执行约定

- 用户是在要求结束本次工作时触发；引用“收工”或仅询问改了什么，不视为调用本流程。
- 不主动修改源码、安装依赖、删除文件或执行 Git 写操作。测试可能产生缓存、报告等文件，不能把执行测试承诺为文件系统零写入；结束前识别其新增内容，不自动清理。
- 每一步取得明确结果后再进入下一步。“失败”“受阻”“未执行并说明原因”也是结果，因此测试失败后仍继续能够完成的审阅、扫描和摘要。
- 每一步结束后立即给出一句可见的阶段记录，再进入下一步；非交互执行也须在过程记录中保留。阶段记录只说明已经发生的事实，不能代替工具调用或在最后补写成已经执行。
- 结果必须有命令、退出码或文件位置等证据。未运行不能写通过；输出中不得包含真实凭证或敏感数据。
- 只对阻塞范围或授权的歧义请求必要信息。没有收到回答时不替用户决定，继续独立可做的检查，并列明缺口。
- 用户另行要求修复时，按授权处理普通修改；修复后从定范围重新核对，再跑受影响测试，不以修复前的结果背书。

## 第 0 步：确定范围

1. 确认工作目录，读取适用的 AGENTS.md、开发说明、测试配置和包管理器约定。
2. 在 Git 仓库记录 HEAD、分支与工作区状态。基线优先采用用户指定或本次工作开始时已记录的 commit；其次采用已确认的目标分支与 merge-base。目标分支不明时不能机械选择 main/master，也不能退回根提交扫描整个历史。
3. 检查范围固定为本次已提交、已暂存、未暂存和新增未跟踪的相关文件。此阶段只读取规则、测试配置、提交信息、文件列表与差异统计；三段范围分别用 name-status、stat 等方式确认。必要时查看测试入口，但不展开完整 hunk、不读取全部变更文件进行审阅。测试取得通过、失败或受阻的明确结果后，才进入第 2 步完整审阅。
4. 建立文件清单，标出属于用户其他工作的内容，只记录不覆盖。无法确认本次基线时说明已覆盖范围，必要时询问，不据此宣称完整收尾。
5. 记录基线、已提交数量、文件数量及未跟踪文件数；数据不可得时写“无法确认”，不猜测。非 Git 项目根据本次修改清单和可用版本对照继续测试、审阅与扫描；没有对照的部分明确列为未验证，不跳过这些步骤。

阶段记录：`定范围完成：基线与三段范围已确认，N 个文件，M 个未跟踪；缺口：无/具体说明。`

## 第 1 步：跑测试

测试方法固定为：**查真实入口 → 按影响选择 → 实际执行 → 记录结果**。

1. 优先遵循项目规则及 CI 配置，其次查 package.json、构建文件或对应语言的测试配置。使用项目指定的包管理器；不能仅凭文件扩展名猜 pytest、npm test 等命令。
2. AI 根据改动与调用关系选择测试范围，说明理由；共享配置、依赖或跨模块变更按项目规则扩大检查。类型检查、lint、DCO 等只在项目要求时追加，并与测试分别记录，不能互相冒充。
3. 使用一次性执行模式，不开启 watch。等待本轮运行结束，不把已启动当通过；未结束的进程保持“运行中”，不重复启动。超时遵循项目或用户预算，只管理本轮启动的进程，不因统一的任意时限终止他人的测试。
4. 失败时由 AI 阅读相关日志、用例与实现，区分已观测事实、原因假设和待验证项，按需要做有针对性的只读排查。不要只摘第一条报错便认定根因，也不要盲目重复运行直到变绿。本流程内不顺手改代码或测试。
5. 无入口、依赖缺失、超时及环境受阻分别记录。不得删测试、跳过失败或修改通过条件制造成功。

每条命令固定记录以下字段；执行器没有提供的信息写“未提供”：

| 工作目录 | 命令 | 选择理由/覆盖范围 | 状态 | 退出码 | 通过/失败/跳过数 | 耗时 | 关键证据或缺口 |
| --- | --- | --- | --- | --- | --- | --- | --- |

状态限于：通过、失败、运行中、超时、未执行。历史结果单独标为历史证据，不能写成本轮执行。

阶段记录：`测试完成：命令，状态，退出码，通过/失败/跳过数；缺口：无/具体说明。` 仍在运行时记录“测试运行中”，不进入完整审阅；明确受阻无法执行时记录原因，再继续审阅。

## 第 2 步：完整审阅改动

- 按文件清单读完每个 hunk，新增文件读内容；分别核对已提交、暂存与未暂存差异，包括删除、重命名、配置和依赖变化。输出被截断时分段补读，不能以统计或模型摘要代替原始差异。
- AI 结合调用上下文判断需求是否实现、错误与边界路径是否合理、是否混入无关改动，核对适用的项目规则和已有测试。发现问题时记录文件、行号、影响和依据。
- 二进制或生成物用合适方式核对来源及结果；无法检查时标明缺口。内部保留逐文件审阅记录，最终摘要只提炼重点。
- 检查阶段产生的新文件或改动加入清单；若代码发生变化，之前的测试结果仅对当时版本有效。

阶段记录：`审阅完成：已覆盖三段差异和新增文件；问题 N 项；未覆盖：无/具体说明。`

## 第 3 步：扫描调试残留

扫描边界固定为：**本次相关文件中，各段差异的新增或修改行、新增未跟踪文件的内容，以及这些文件的名称**。需要解释命中时再读其上下文，不把全仓既有日志当作本次新增问题。未跟踪文件单独列出，不能依赖 git diff。

先按已提交、暂存、未暂存三段差异提取准入行，并单独列出新增未跟踪文件。每条命中必须标明所属来源及该版本的文件行号，核对它确实属于相应新增/修改行；不属于准入行的候选不得计入扫描结果。读取的上下文和未修改的 AGENTS.md 只作判断依据，不算命中。暂存区保留、工作区已删除的内容仍以“暂存版本”记录，不能用工作区内容抵消。

1. 用 rg 或当前环境的等价工具搜索调试输出、断点、仅跑/跳过测试、临时开关与端点、固定测试值、TODO/FIXME 及临时文件名等线索。按项目语言补充关键词；固定 ID、时间、mock、localhost 等还需结合审阅判断，不能只靠正则。
2. 疑似密钥只报告文件位置及已脱敏的类别，不把匹配原文输出到报告或日志。搜索命令无命中与执行失败必须区分；只有扫描完成才能报告“0 命中”。
3. 每个命中都由 AI 阅读上下文，判断是否为临时残留，不能按关键词批量删除，也不能认定所有测试 fixture 都合法或所有绝对路径都是残留。

固定记录：`来源（已提交/暂存/未暂存/未跟踪）｜文件:该版本行号｜明确残留 / 合法用途 / 待确认｜准入与判断依据`。临时文件用文件路径代替行号；二进制或无法扫描项明确列为缺口。同一内容在多个来源重复出现时保留来源但不重复计数，并说明合并方式。明确残留列为待清理，合法项说明保留理由，不确定项列为需确认。**本流程只报告，不自动清理。**

阶段记录：`扫描完成：N 处残留、M 处合法用途、K 处待确认；命中来源与准入行已核对；缺口：无/具体说明。` 核对失败的候选不计入命中，写明尚未完成范围检查。

## 第 4 步：输出简短摘要

模板和字段固定，内容由 AI 理解后生成。通常控制在 6～10 行；测试命令或阻塞项较多时，在摘要后附前述明细，不能为了行数隐去失败和未验证项。

```markdown
结论：可以收工 / 尚未完成（原因）
范围：基线与覆盖范围；N 个文件，M 个未跟踪；未确认部分
改动：1～3 条关键变化及目的
测试：关键命令 → 状态；通过/失败/跳过数，退出码与耗时；详见测试记录
审阅：覆盖情况、关键问题与证据位置
扫描：命中数及分类；无命中写“本次范围内未发现临时调试残留”
待办：待清理、需确认和未验证项；没有则写“无”
```

只有范围明确、必要测试通过、审阅和扫描完整、无阻塞问题与待清理残留时写“可以收工”。受阻时继续报告已完成的部分，不以“整体不错”代替证据。
