# 收工

目标：按固定顺序给出有证据的收尾结论。收工检查本身不授权自动 commit、push、合并或发布；这些操作沿用用户已有的明确指令。

## 准备：确定本次范围

1. 确认工作目录，读取适用的 AGENTS.md、项目开发说明、测试配置和包管理器配置，遵循既有规则。
2. 在 Git 项目中查看分支、工作区和暂存区状态，记录检查开始时的 HEAD。范围包含本次已提交、已暂存、未暂存以及新增未跟踪的相关文件，不能只看 git diff 或只看暂存区。
3. 优先使用当前工作记录或用户指定的起点作为本次基准；没有时，根据已核实的目标分支及 merge-base 确定分支范围。无法确定时说明仅覆盖可确认范围；若仍有多个可能范围且会影响结论，询问起点，不猜成“整个仓库”或“没有改动”。非 Git 项目使用已有修改清单和文件版本，缺少对照时说明限制。
4. 列出待检查文件，区分本次工作与用户其他未完成工作。不得覆盖或回退用户已有修改。

## ① 跑一遍测试

1. 从项目文档、CI 或真实配置查找测试命令，使用项目指定的包管理器和测试入口，不臆造命令。根据本次影响选择相关测试；涉及共享配置、依赖或跨模块行为时，遵循项目要求扩大范围。无改动时执行项目约定的默认检查。
2. 实际运行所选测试，记录工作目录、完整命令、退出码及结果。已有进程仍运行时等待其完成，不把“已启动”算通过，不重复启动同一检查。记录哪些范围未覆盖。
3. 测试失败、依赖缺失或命令不可用时保留事实和错误摘要，继续能够完成的审阅步骤；不写“全部通过”，不删除、跳过或弱化测试制造通过。没有可用测试入口时说明“未执行：原因”，不把其他检查冒充测试。已有测试结果只有在对应代码未变且范围匹配时才可引用，并注明非本轮执行。

## ② 从头到尾看完本次改动

1. 对照准备阶段的完整文件清单，逐个阅读实际差异：分支已提交范围、暂存区、工作区分别检查；阅读新文件内容，也检查删除、重命名和配置变化。差异输出被截断时分段补读，直到清单中的文件均已覆盖。
2. 结合调用方、配置和已有测试判断改动是否实现需求，是否引入明显错误或遗漏边界。不能用 diff 统计、测试通过或 AI 自己的完成报告代替审阅。
3. 记录发现的具体问题、文件位置与影响。无法直接阅读的二进制或生成物，使用适合的查看方式或检查其来源与生成结果；做不到则标明未验证，不能声称看完。

## ③ 专门检查临时调试代码

1. 在本次变更文件中搜索并逐项阅读可疑代码，例如 console.log、debugger、print、临时调试开关、mock、写死的测试值、跳过测试、临时端点及凭证。使用项目语言对应的搜索方式，并复核上下文；关键词只是线索，未命中也不能替代代码审阅。
2. 区分临时残留与正式日志、合法默认值、测试夹具，不按关键词批量删除。输出的错误摘要不得泄漏凭证或敏感数据。
3. 对明确的临时残留，若当前任务已授权修复且不涉及用户其他修改，做最小修正；归属或用途不清时列为待确认，不擅自删除。检查结束仍有未解决残留时，不能给出“可以收工”的结论。
4. 检查开始后的任何修正，以及测试产生的新改动，都要更新文件清单。重跑受影响测试，并重新审阅新增差异、检查残留；已验证且未受影响的测试不重复跑。再次检查 Git 状态，不能遗漏检查期间产生的变更。

## ④ 输出简短摘要

固定使用以下四项，并在第一行给出“可以收工”或“尚未完成”。只有范围明确、应做测试通过、改动审阅完整、没有未解决的阻塞问题或临时残留时，才写“可以收工”。未执行测试或存在无法核验的范围时，说明实际完成到哪一步。

- 改动：用 1～3 句话说明做了什么、目的是什么。
- 测试：命令、结果，以及未执行项和原因；长输出只摘关键证据。
- 审阅与残留：覆盖范围、发现或修正的问题；未发现时写“本次检查范围内未发现临时调试残留”，不作绝对保证。
- 待办：未解决问题、未覆盖范围或需要用户处理的事项；没有则写“无”。
