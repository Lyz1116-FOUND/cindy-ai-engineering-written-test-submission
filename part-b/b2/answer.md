# B2：收工 Skill

## (a) SKILL.md

完整文件：[end-of-work/SKILL.md](end-of-work/SKILL.md)。

用户说“收工”时，按“定范围 → 跑测试 → 审阅 → 扫描 → 摘要”执行。测试、审阅和扫描是必须完成的动作，失败或受阻也必须有明确记录；摘要的形式固定，内容由 AI 理解后生成。

本流程使用 Agent 已有的文件、Git 和终端工具，不主动修改代码、清理文件、提交或推送。测试可能生成缓存和报告，这些变化需要记录，不能声称执行测试一定零写入。

## (b) 哪些固定，哪些交给 AI

我的原则是：由我固定流程、事实记录与呈现方式，把需要理解项目、判断和解释的部分交给 AI。

| 环节 | 我固定的动作与形式 | AI 理解和判断的部分 |
| --- | --- | --- |
| 触发与顺序 | 定范围 → 跑测试 → 审阅 → 扫描 → 摘要，不漏步骤 | 根据工作记录确认本次改动基线；不确定时说明或询问 |
| 测试方法 | 查项目真实入口、实际执行、记录结果；失败不冒充通过 | 判断受影响范围、选择具体命令，探索失败原因 |
| 测试记录 | 固定记录目录、命令、范围理由、状态、退出码、通过/失败/跳过数、耗时和证据 | 理解结果是否合理，区分现象、原因假设和未验证项 |
| 改动审阅 | 从头到尾读完本次差异及新增文件，不能只看统计 | 理解变化目的，判断边界行为、遗漏和风险 |
| 扫描 | 固定扫描本次新增/修改行、新增未跟踪文件及文件名，命中按位置、分类、理由记录 | 判断 console.log、固定值、mock 等是临时残留还是合法用途 |
| 摘要 | 使用结论、范围、改动、测试、审阅、扫描、待办的固定模板 | 理解后提炼重点，用简短说明解释变化和风险 |

这样每次的流程与结果形式一致，人能很快找到重点；项目相关的含义由 AI 判断。比如 console.log 可能是调试输出，也可能是 CLI 的正式输出，不能用固定规则一律删除。测试范围也不能跨项目写死成同一条命令。

固定的是记录事实的方法，不是预设运行结果或失败原因；结果必须实际观察，原因需要探索和证据。

## (c) 为什么适合 Skill，而不是插件

这是一个工作流程：用户直接在会话中调用，AI 用现成工具检查本地仓库，再在同一会话输出摘要。它不需要单独面板、新的 Agent 能力、专门交互结构或脱离会话运行，也不需要为流程新增网络接入。

Skill 的文本可以直接审阅和修改，下一次加载时就能采用新规则，不必维护插件的 UI 和打包流程。同一份正文可以给具备对应加载与工具能力的 Claude Code、Codex、Pi 复用；安装位置和触发方式按宿主配置。

当前需求只需把工作方法写清楚，Skill 足以承载。未来若要常驻看板、集中状态或专用数据接入，再考虑插件提供这些能力。
