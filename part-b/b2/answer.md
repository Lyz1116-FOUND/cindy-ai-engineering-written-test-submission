# B2：收工 Skill

## (a) SKILL.md

完整文件：[skills/wrap-up/SKILL.md](skills/wrap-up/SKILL.md)。

用户说“收工”时，先确定项目与本次改动范围，然后按顺序执行：跑测试、完整阅读改动、检查临时调试残留、输出简短摘要。测试或审阅有缺口时如实报告；修正代码后重新验证受影响部分，避免用修改前的通过结果为修改后的代码背书。

Skill 自包含，不依赖 Cindy 专有 API。支持 Skill 的 Agent 可加载该目录；其他 AI 也可直接读取正文按流程执行，实际效果仍取决于它拥有的文件和执行工具权限。

## (b) 固定动作与 AI 判断

| 环节 | 固定动作 | 可以交给 AI 判断的部分 |
| --- | --- | --- |
| 确定范围 | 确认工作目录、读取规则、列明检查起点和文件清单 | 如何根据实际工作记录与 Git 关系确定本次范围；不确定时指出缺口 |
| 跑测试 | 查真实测试入口、实际执行、记录命令和结果；失败不能宣称通过 | 根据改动影响选择相关测试，以及是否需要扩大到跨模块或完整测试 |
| 看改动 | 完整覆盖本次已提交、暂存、未暂存和新增内容；输出被截断须补读 | 判断实现是否符合需求，调用关系和边界行为是否存在问题 |
| 查调试残留 | 必须搜索、逐项读上下文，并在结束前复核状态 | 区分临时残留、正式日志、合法默认值及测试夹具；判断能否在授权范围内修正 |
| 修正后验证 | 更新清单，重跑受影响测试，复核新增差异 | 判断此次修正影响哪些测试和调用路径 |
| 摘要 | 固定输出改动、测试、审阅与残留、待办；结论必须对应证据 | 提炼最重要的变化、风险和下一步，控制篇幅 |

固定的是顺序、覆盖范围、证据要求和失败处理，使每次都不会漏步骤。保留判断的是项目相关的语义：不同项目的测试入口不同，console.log 可能是临时输出，也可能是 CLI 的正式功能。把这些写成统一删除规则或固定 npm test，会产生误删和误判。

“每次一样”指相同的流程与完成标准，不要求在不同项目机械运行相同命令，也不保证模型永远作出相同判断。

## (c) 为什么适合 Skill

这是对已有文件、Git、终端和测试能力的流程编排，主要需求是让 AI 按既定顺序工作、用证据判断是否完成，并给人一份简短报告。Skill 可以直接承载这些规则，随项目复用。

它目前不需要独立面板、专用后台、外部服务接入或新的权限接口，因此没有必要为了流程新增插件运行时和 UI。只有将来需要可交互的跨项目测试看板、集中状态或专用服务连接时，才考虑插件承载界面或数据能力；收尾规则仍可保留在 Skill 中。
