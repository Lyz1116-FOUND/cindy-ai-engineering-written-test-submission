## 用户决定哪些部分

固定顺序是“定范围 → 跑测试 → 审阅 → 扫描 → 摘要”。必须跑测试、看完整改动、查残留；测试方法与结果字段、扫描边界、摘要结构也固定，使每次的重点容易找到。

这里的“事实类固定”落实为必须做什么、检查到哪里、记录哪些事实、用什么形式报告。实际退出码、失败数等必须来自运行，不能预先规定成通过。

## AI 判断哪些部分

AI 结合项目结构选择具体测试范围，阅读结果并判断是否合理；结合代码上下文解释扫描命中是否为临时残留；遇到失败时主动查日志、用例和实现，不止抄一条错误。最后在固定模板里提炼变化和解释风险。

“测试方法固定”和“测试范围由 AI 判断”可以同时成立：方法固定为查真实入口、按影响选择、实际执行、记录证据，具体跑哪些命令由项目规则和本次改动决定。

## Skill 底稿的润色与修正

保留原稿的五步顺序和不主动改代码、提交、推送、清理文件的边界，修正以下执行问题：

1. “上一步没有结果”明确包含失败或受阻结果，避免与“不跳步”冲突。
2. 不把未知目标分支机械当作 main/master，也不退回根提交扫描全部历史；分开审阅已提交、暂存、未暂存，避免合并 diff 抵消后漏看。
3. 非 Git 项目继续依据修改清单做审阅和扫描，不直接跳过。
4. 不笼统承诺文件系统只读：测试可能生成报告或缓存；不自动修改业务代码和清理文件。
5. 扫描命中先解释用途，不把所有 fixture 认定合法；疑似凭证只报位置，不输出原文。删除了会直接打印匹配内容的长扫描脚本，保留扫描边界与记录合同。
6. 不固定任意十分钟超时，不把超时等同于断言失败；超时或未完成分别记录。
7. 固定摘要模板，但测试明细多时允许附表，避免“八行上限”与“每条命令都要记录”冲突。

## 为什么采用 Skill

按用户原意，这是已有本地 Git、终端与文件能力的流程，不需要独立面板、新能力或脱离会话运行。检查方法本身不新增联网依赖；具体项目的测试是否联网由项目决定。

规则是可审阅文本，修改后在 Agent 下一次加载时生效；具备对应 Skill 加载及工具能力的 Claude Code、Codex、Pi 可以复用正文。触发方式、发现目录和权限仍按各宿主配置，不承诺所有宿主自动发现同一路径或即时热更新。
