## (a) SKILL.md

设计上只做四件事，让“每次一样”落在可核对的动作上：

1. **触发词写进 description**：只在用户说「收工」时说，不把普通总结也吸进来。
2. **顺序写死**：定范围 → 跑测试 → 审阅 → 扫描 → 摘要，上一步没有结果不进下一步。
3. **取证写死**：基线、测试命令、退出码、扫描范围、摘要模板都有明确格式；未跟踪文件单独扫，因为 `git diff` 看不到它们。
4. **只读写死**：收工不提交、不推送、不删文件、不顺手修 bug；需要修改时退出本流程。

````markdown
# 收工

按固定顺序完成收尾：**定范围 → 跑测试 → 审阅 → 扫描 → 摘要**。目标是让不同的人或 AI 每次得到同样的结果，而不是自由发挥一份“看起来不错”的总结。

## 触发

- 触发：「收工」「收尾」「今天到这」「下班」「wrap up」。
- 不触发：只问「刚才改了什么」→ 直接回答；只想提交或发 PR → 按对应流程处理。本 Skill 不包含提交、推送和发 PR。

## 不变量

1. **顺序固定**，上一步没有结果不进入下一步。
2. **只读**：不执行 `git add`、`commit`、`push`、`stash`、`reset`、`clean`、`checkout`；不改源码；不删文件；不安装依赖。
3. **不跳步**：测试失败也要完成审阅、扫描和摘要。
4. **只报看到的**：结论必须带证据（命令、退出码、`文件:行`）；没运行的项写“未运行”，不能写成通过。
5. **有歧义先问一次**：只问阻塞当前步骤的问题，问完继续。

如果用户要求顺手修复，先说明“这会离开收工流程”，按普通任务修改；完成后重新从第 0 步收工。

## 第 0 步：确定范围

```bash
git rev-parse --show-toplevel
git status --short
```

确定基线 `BASE`：

1. 用户或本会话已指定基线 → 用它。
2. 否则依次尝试 `origin/main`、`origin/master`、`main`、`master`，取第一个存在的，运行 `git merge-base <ref> HEAD`。
3. 都不存在 → `git rev-list --max-parents=0 HEAD | tail -n 1`。

```bash
BASE=<上一步结果>
git log --oneline "$BASE"..HEAD
git diff --stat "$BASE"
git ls-files --others --exclude-standard
```

- 若 `BASE..HEAD` 中有不是本次会话产生的提交，或用户说的“这次”与分支历史不一致，**停下来问一次**用哪个基线；得到答复后继续。
- 记录：基线、提交数、改动文件数、`+A/−D`、未跟踪文件数；摘要中必须出现。

不在 git 仓库时：记录“无 git”，跳过第 0、2、3 步，第 1 步照常尝试，摘要注明。

## 第 1 步：跑测试

按下列顺序选择命令，**选到第一条就停止**：

| 顺序 | 条件 | 命令 |
| --- | --- | --- |
| 1 | 仓库根 `AGENTS.md`、`CLAUDE.md` 或 `CONTRIBUTING.md` 写明了测试命令 | 照它执行 |
| 2 | 根 `package.json` 有 `test:unit:related` | 用对应包管理器运行 `test:unit:related`（lockfile 为 pnpm 时即 `pnpm test:unit:related`） |
| 3 | 根 `package.json` 有 `test` | 按 lockfile 用 pnpm / yarn / npm 执行 `test` |
| 4 | 其他生态 | `pytest -q` / `go test ./...` / `cargo test` / `swift test` |
| 5 | 以上都没有 | 不猜；记录“未找到测试入口” |

范围：

- 改动路径向上找到最近的 `package.json`，取其 `name`，去重；用仓库对应的包管理器对每个受影响的包运行类型检查（Cindy 仓库为 `pnpm --filter <包名> run --if-present typecheck`）。
- 仓库规则要求全量、或改动跨多个包时，才扩大范围；不为了“更保险”默认跑全量。
- 不使用 `--watch`。

记录并写进摘要：每条命令、退出码、通过/失败数、耗时。测试超时（单条命令 10 分钟）按失败记录并终止。失败时记录首个失败用例和首条错误，**不在收工流程内修复**，继续第 2 步。

不得用 `--no-verify`、`--passWithNoTests`、跳过用例等方式把失败变成通过。

## 第 2 步：从头到尾审阅改动

“从头到尾”指**每个 hunk 都要读**。禁止只看 `--stat`、只看文件名，或让另一个模型代读后只取摘要。

```bash
git diff --check "$BASE"
git diff --name-status "$BASE"
git diff "$BASE" -- .
git ls-files --others --exclude-standard
```

- 逐个文件读完整 diff；未跟踪文件逐个读全文。
- 有 commit 且 `package.json` 有 `check:dco` 时运行 `check:dco`（用对应包管理器；Cindy 仓库为 `pnpm check:dco`）。
- 对每个文件回答：
  - 改了什么，为什么（只能写 diff 和上下文能支持的理由）；
  - 是否误删文件、意外整文件格式化、混入锁文件/二进制/大文件；
  - 边界、错误路径、权限与安全（密钥、token、真实用户数据、本机绝对路径）；
  - 是否留下写死的测试值（固定 ID、固定时间、mock 数据、`localhost` 地址）；
  - 仓库规则是否满足（如 UI 双模式、i18n、测试、DCO）；
  - 新增行为是否有对应测试。
- 产出：每个文件一行“改了什么”，供第 4 步使用。

`git diff --check` 报出的冲突标记或空白错误必须记录；冲突标记视为阻塞问题。

## 第 3 步：扫描遗留调试代码与临时文件

`git diff` 看不到未跟踪文件，所以必须扫两个来源。只扫**本次新增**内容，避免把仓库里既有的日志全部翻出来。

```bash
PATTERN='console\.(log|debug|trace|dir)|debugger|alert\(|\.only\(|(it|test|describe)\.skip|TODO|FIXME|XXX|HACK|pdb\.set_trace|breakpoint\(|fmt\.Print|System\.out\.print|ghp_[A-Za-z0-9]{20,}|sk-[A-Za-z0-9]{16,}|AKIA[0-9A-Z]{16}|/Users/[A-Za-z]'

# 1) 已跟踪文件的新增行（带 文件:行号）
git diff -U0 "$BASE" -- . | awk '
  /^\+\+\+ b\// { f=substr($0,7); next }
  /^@@/ { if (match($0, /\+[0-9]+/)) ln=substr($0,RSTART+1,RLENGTH-1)+0; next }
  /^\+/ && !/^\+\+\+/ { print f ":" ln ":" substr($0,2); ln++ }
' | grep -E "$PATTERN"

# 2) 未跟踪文件
git ls-files --others --exclude-standard -z | while IFS= read -r -d '' f; do
  grep -nHIE "$PATTERN" -- "$f"
done

# 3) 临时文件名
git ls-files --others --exclude-standard | grep -E '(^|/)(\.DS_Store|nohup\.out|.*\.(log|tmp|bak|orig|rej|swp))$'
```

`grep` 无命中时退出码为 1，属正常。不得把“没有输出”当成“扫描通过”，要在摘要里写“扫描 0 命中”。

把每个命中分到三类，逐条给出 `文件:行` 和理由：

| 类别 | 判定 | 处理 |
| --- | --- | --- |
| 明确残留 | 调试输出、`debugger`、`.only`、无理由的 `skip`、临时文件、真实 token 或本机绝对路径 | 列入摘要“待清理” |
| 可能合法 | logger 实现、CLI 的预期输出、断言 `console` 的测试、带 issue 链接的 `skip`、示例代码 | 保留，写明理由 |
| 不确定 | 无法从上下文判断 | 列入摘要“需确认” |

写死的测试值（固定 ID、固定时间、mock 数据、`localhost` 地址）无法用正则可靠识别，在第 2 步按文件判断；测试文件内的 fixture 不算残留。

**本轮不清理**。用户明确要求清理时，另开普通任务：先列清单，删除未跟踪文件前逐项确认。

## 第 4 步：输出摘要

只输出下面这个结构，正文不超过 8 行：

```markdown
## 收工摘要
范围：<BASE>..工作区，N 个文件（M 个未跟踪），+A/−D
改动：<2–4 条，按模块，每条一句>
验证：<命令> → 通过/失败（X 通过 / Y 失败，Zs）
残留：无 / <文件:行> / N 处待确认
风险：<未验证项、既有失败、需要决定的事>
```

- 测试失败、有明确残留或发现阻塞问题时，**第一行先写结论**，不要埋在最后。
- 只写结论和证据：不复述 diff，不逐个文件罗列，不写“整体来看质量不错”这类评价。
- 没有验证的项必须出现“未验证”字样。

## 停止条件

遇到下列情况停止当前动作并说明，不要自行绕过：

- 需要 `sudo`、联网安装依赖、修改仓库外文件或执行其他破坏性命令；
- 测试命令与仓库文档冲突，或仓库文档要求先征得维护者同意；
- 连续两次测试失败原因不同（可能是环境不稳定），仍按失败记录，不强行重跑到通过；
- 用户中途改变要求：按新要求执行，摘要中列出未执行项。
````

## (b) 哪些写成固定动作，哪些交给 AI 判断

### 划分标准

1. **结果能否用命令取证**：能稳定复现、输出可核对的动作固定下来。
2. **错一次的代价是否不对称**：漏掉失败、漏扫临时文件、误删合法日志，代价远高于多花几分钟，需要固定检查兜底。
3. **是否需要理解意图**：要读代码上下文才能回答“为什么改”“这条日志是否合法”的，交给 AI。

固定动作负责**取证**，AI 负责**解释**。这是分界的核心：固定步骤产出事实（命令、退出码、命中位置），AI 不得跳过或改写这些事实；判断结论必须引用这些事实。

### 固定动作

| 固定动作 | 具体内容 | 为什么不能交给 AI 自由发挥 |
| --- | --- | --- |
| 四步顺序 | 范围 → 测试 → 审阅 → 扫描 → 摘要 | 顺序影响证据完整性；先写摘要再看 diff，会按结论找证据 |
| 基线计算 | 指定基线 → `origin/main` 等合并点 → 根提交；有历史混入时问一次 | “这次”必须有可复现的起点；随手用 `git diff` 会漏掉已提交内容和未跟踪文件 |
| 测试命令选择 | 仓库文档 → `test:unit:related` → `test` → 各生态默认命令 → 记录“无入口” | 让模型自由选，常见结果是只跑一个子包、或凭空猜命令 |
| 测试结果记录 | 命令、退出码、通过/失败数、首个失败用例；超时按失败 | 不记录退出码就无法区分“跑过”和“通过” |
| 扫描范围 | 只扫本次新增行 + 未跟踪文件；固定正则；固定三类分桶 | 扫全仓会把既有日志全部翻出来；只看 `git diff` 会漏掉未跟踪的临时文件（已实测，见下文） |
| 摘要模板 | 固定字段、正文 ≤ 8 行、失败/残留置顶 | 不固定就会每次长度、结构、重点都不同，无法快速比较 |
| 只读红线 | 不提交、不推送、不删除、不顺手修 | 收工是检查点，不是修改点；自动“顺手清理”不可逆且扩大 blast radius |

这些动作的输出是“事实”，不同模型执行应当得到可对比的结果；它们也恰好是模型最容易省事的地方：只看 `--stat`、漏 untracked、把“没有输出”当“没有残留”。

### 交给 AI 判断

| 判断点 | 具体问题 | 为什么不能写死 |
| --- | --- | --- |
| 本次边界 | 分支上的早期提交算不算“这次” | 依赖会话历史；规则只能给出默认基线，冲突时必须问一次 |
| 测试范围是否足够 | related 选测够不够，是否要全量/集成测试 | 取决于改动影响面，正则和目录规则无法可靠判断 |
| 命中项是否合法 | `console.log` 是调试残留，还是 logger/CLI/测试断言 | 同一行代码在不同上下文结论相反；写死会误删 |
| 失败归因 | 本次引入、既有失败、环境问题还是 flaky | 需要读错误、比较基线、判断是否与本 diff 相关 |
| 改动分组与风险 | 按模块怎么归纳、哪条风险最高、哪些未验证 | 需要理解代码语义和产品影响，属于解释工作 |
| 是否停下来问 | 基线冲突、命令与仓库规则冲突、需要 sudo/联网 | 无法穷举；固定的是“遇到就停”的原则，不是具体触发条件 |

写死这些判断会产生两类更贵的错误：**假阳性**（把合法日志当残留删掉、把 flaky 当回归去改代码）和**假阴性**（把真实回归说成环境问题）。宁可让 AI 在固定证据上做判断，并允许它把不确定项交回用户。

### 为什么不全部固定或全部交给 AI

- **全部固定**：②③ 的输入是开放文本，任何正则都无法覆盖“写死的测试值”“看起来像调试但其实是功能”的情况，固定规则只能制造误报。
- **全部交给 AI**：每次的步骤、命令、摘要结构都会漂移，而且模型倾向于跳过昂贵步骤（跑测试、读完整 diff）。固定动作把“必须做”变成可检查的清单。
- **混合的收益**：固定部分可以脚本化、可回归测试；判断部分保留解释空间，但被要求引用证据。这样既一致，又不僵化。

## (c) 为什么这件事适合做成 Skill，而不是插件

### 按仓库自己的分工判断

`docs/product-rules/core-product-principles.md` §5 写得很明确：

- Skill 描述工作如何完成，用自然语言、脚本或工具编排已有能力，适合沉淀反复出现的工作方法，通常不需要专属交互界面（:194-195）。
- 插件是可运行的小程序，负责承载富交互、结构化状态和专用能力（:197-199）；§4.4 称其为“运行在 Cindy 中的沙箱小程序”（:159）。
- §6 的归属规则：工作流程进入 Skill；外部能力、数据接入和富交互界面进入插件（:207-208）。

收工流程正好落在 Skill 的定义上：它是每天重复的工作方法，编排的是 Agent 已有的 git、shell、测试和读文件能力，产物是一段固定格式的文本。

### 逐条对照插件的适用条件

| 判据 | 收工流程 | 结论 |
| --- | --- | --- |
| 需要 Agent 没有的新能力？ | 不需要：git、shell、测试运行器、文件读取都是现成的 | 不构成插件理由 |
| 需要富交互或结构化状态？ | 不需要：输出是 Markdown 摘要 | 不构成插件理由 |
| 需要脱离 Agent 自主运行？ | 不需要：用户一句话触发，Agent 在环 | 不构成插件理由 |
| 需要网络、凭证或持久后台？ | 不需要：只读本地仓库 | 不构成插件理由 |

### 做成插件的成本

插件不是“把提示词换个地方放”，它要承担一整套运行时与分发成本：

- 身份卡与能力声明、沙箱边界（§4.4，:157-173）；
- 安装、批准状态与内容摘要（`docs/dev-rules/plugin-security-and-authoring.md:34`）；
- 打包、安装、发布与签名流程（`apps/desktop/resources/system-skills/cindy-plugin-creator/SKILL.md:19`）；
- 宿主 API 的版本绑定与跨版本兼容；
- 任何 UI 都要实现 Light/Dark 两种模式。

这些成本换不来新能力。更关键的是：插件最多把 ① 跑测试和 ③ 的正则扫描自动化；② 的“看懂改了什么”、③ 的“这条是不是残留”、④ 的“风险和未验证项”仍然要判断。插件当然可以再调用模型，但那等于在插件里复制一份 Agent 已有的会话上下文、工具循环和判断口径，还要自己维护提示词与模型配置——这是重复实现，不是新能力。

### Skill 的额外优势

- **可审阅**：纯文本，团队可以在 PR 里看 diff、改一句就生效，不用重新打包、安装、确认权限。
- **可移植**：同一份 Skill 可被 Claude Code、Codex、Pi 共用，不绑定宿主版本；插件绑定具体宿主 API。
- **权限面小**：收工是只读流程，放在对话里，用户能看到每条命令并随时打断。插件是具备声明能力的沙箱程序，可自主运行，blast radius 更大，而这里没有需要它的能力。
- **发布范围匹配**：这是个人/团队的工作习惯，不是所有用户共同依赖的宿主能力；按 §6，不应进入 Core，也不需要用插件承载。

### 什么时候值得升级为插件

如果以后需要以下任一能力，再考虑“插件 + Skill”的组合：

- 常驻面板展示历次收工记录、测试趋势和残留清单；
- 定时或在收工后自动运行（Agent 不在环）；
- 一键触发 CI、跨机器收工或写入团队看板。

这些都需要富交互、持久状态或脱离 Agent 的执行，符合 §6 的插件条件。即便如此，流程口径仍应留在 Skill 里，插件只做触发器和界面——§5 明确说两者可以配合：“Skill 决定工作流程，插件在合适阶段提供查看、编辑、判断和操作界面”（:200-201）。

## 依据与验证

### 已运行
