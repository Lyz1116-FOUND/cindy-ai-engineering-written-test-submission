# B1(a) 我的 PR 看板：设计判断

> 本文是写代码前的设计答案。实现、运行截图及排查记录在 B1(b) 实作后补充，不以设计文档代替运行结果。

## 1. 采用可关闭、可重新打开的常驻面板

用户查看 PR 不应以启动 Agent 为前提。看板需要并列显示多条 PR、比较 CI 状态、刷新并选择分析对象，因此采用插件侧栏面板，开关由 UI 完成。

纯工具适合按需查询，聊天卡片适合展示单次结果，都不如面板适合作为这个功能的主要入口。这里的区别是操作和呈现方式，而不是工具不能保存历史。偏好与必要的缓存通过插件存储保存，不能假设面板和后台逻辑始终存活。

## 2. 看板采用插件自主联网，并声明对应能力

打开面板和点击刷新时，可能没有正在运行的 Agent 调用，因此插件需要自主访问 GitHub，声明 `api.github.com` 等实际必需域名，通过宿主代理请求。

这与 AI 正在调用插件工具时的联网不同：当前作者契约允许在真实 tool-call 内带 `callId` 访问未预声明的普通 HTTPS 地址。自主联网需要域名白名单；使用宿主托管凭证时，无论哪条路径，凭证和注入域名都须显式声明。两种路径都受宿主网络检查，插件面板不能自行绕过代理直连。

## 3. 用户提供 GitHub 凭证，由宿主凭证库保存

最小版本使用用户提供的 PAT，通过宿主配置入口安全收单并加密保存，HTTP 请求时由宿主注入。插件只读取配置状态，不读取保险库中的 token 明文；不把 token 放进聊天、源码、日志、普通 KV 或广播消息。

OAuth 可以改善连接体验，但必须有真实的应用配置和用户授权，不能因为产品要求避免重复确认，就推断 AI 能替用户完成授权。第一版先完成 PAT 路径。也不采用官方 `cindy-github` 专属的 `source:"gh-cli"` 凭证来源。

## 4. 插件整理证据，AI 解释 CI 失败原因

点击“分析 CI”后，插件先收集仓库、PR 标题与链接、分支、当前 head SHA、失败检查及可获得的失败步骤、截断日志和原始链接，再把这些资料和分析问题一起交给 AI。

插件完成取数、状态映射和展示；AI 判断可能是编译错误、测试失败、环境问题等，并区分已有证据和待验证推测。怀疑 flaky 时需要历史或重跑证据。普通 GitHub API 足以承担数据获取，不必依赖 Computer Use；只把链接交给 AI、假定它已有 GitHub 登录和工具，不足以保证接手成功。

交接方式按实际场景选择：

- AI 已在调用 `get_pr_ci` 时，直接返回结构化工具结果，让当前 AI 继续分析，不再创建额外任务。
- 关联已有任务的卡片交互，按 `agent.run` 的真实点击票与任务关联契约继续。
- 独立面板发起分析时，使用实际宿主支持的公开独立任务接口。优先核验 `cindy.tasks.create/send`；本地实现文档仍标为实验、尚未发布，不能预设已安装版本支持。若不支持，则核验该版本的 `agent.errand/queryErrand` 能否完成可见任务及结果查询。

第一版让 AI 在用户可查看、可接手的任务里分析，面板展示交接状态及可用的任务入口。结果回填面板可后续增加。创建成功或输入被接受只表示交接已受理，不能显示为分析完成；失败应保留原因和可恢复入口。

## 实作范围与依据

第一版把“我的 PR”明确为授权范围内我创建的、仍打开的 PR，处理分页，展示 CI 状态并支持点击分析。无检查、运行中、失败和获取失败分别呈现；数据绑定 head SHA，不能用旧日志解释新提交。

依据为 Cindy 源码中的以下文档，路径相对于 Cindy 源码仓库：

- `apps/desktop/resources/system-skills/cindy-plugin-creator/references/plugin-panels.md`：面板形态、生命周期、通信及主题。
- 同目录 `plugin-network.md`：自主联网、在途调用、凭证保存与 gh-cli 限制。
- 同目录 `plugin-agent-tasks.md`：工具结果、run、errand 和普通任务交接边界。
- `docs/dev-rules/plugin-task-api-implementation.md`：普通任务接口的实验状态。
- `docs/product-rules/core-product-principles.md`：插件承载专用交互与外部数据，Agent 承担推理执行。

本地源码尚未与实际执行宿主的版本绑定。具体 API、能力声明及最小版本在写代码前核验，并在 README 记录实际采用的路径。
