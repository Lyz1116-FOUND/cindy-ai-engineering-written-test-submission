## Part 0 上手题

### 0a 项目导览

Cindy 是连接用户、设备、Agent 和模型的 AI 工作客户端。模型生成内容，Agent 组织上下文与工具执行，Cindy 提供界面、系统能力与多端连接。本仓包含客户端，服务端在独立仓库。

主要部分：apps/desktop 是 Electron 桌面端，renderer 绘制界面、preload 暴露受控接口、main 负责系统能力与持久化；apps/mobile 是 Expo / React Native 手机端；packages/maker-core 负责 Agent 抽象与编排；device-link、model-providers、plugin-protocol 分别处理跨设备协议、模型供应商目录与插件契约。普通消息简化路径为 renderer → preload → main → maker-core Session → 具体 Agent 引擎。依据：docs/dev-rules/repo-map.md。

插件能力依据在 apps/desktop/resources/system-skills/cindy-plugin-creator/references/：plugin-settings.md、plugin-files-and-library.md 说明 KV、私有文件与 Library；plugin-network.md 说明联网代理和宿主凭证；plugin-runtime.md §4.0.2 说明 oneshot_text；plugin-agent-tasks.md 说明 Agent 任务交接；plugin-panels.md、plugin-chat-cards.md 说明界面能力。ghost.json 声明所需能力，运行时仍由宿主校验。

我先读 README、AGENTS.md 和仓库地图，再集中看插件声明与作者手册；AI 帮我检索、静态核对调用链和整理笔记，我重点理解 fs、Library 和 Agent 接口的区别。Part 0 阶段没有启动应用或运行测试，后续 B1 才进行了实机验证。

### 0b 每日单词卡

例句生成只需一次文本回答，使用宿主 oneshot_text：在 ghost.json 声明 cindy.text 的 oneshot 能力，通过 cindy.send 发起请求；插件负责十词输入、场景、输出校验和当日缓存。依据：上述 plugin-runtime.md §4.0.2，以及 apps/desktop/src/main/cindy-brain/cindySlot.ts 的 handleOneshotText。

## Part A 判断力

### A1 日期参照问题

（a）我同意自动提供日期，但不同意把每次变化的秒级时间戳加进稳定 system prompt 后直接上线。前缀缓存依赖相同内容，变化点之后的缓存可能失去复用，历史消息并不会因此消失；同时还没定义用户时区。知道今天几号，也不等于知道本周发生的新消息。

（b）短对话可能答对且不报错，但经过修改点、原本可复用前缀缓存的请求可能增加未命中计算、费用和首 token 延迟，长上下文和多步任务更值得关注。影响取决于时间戳位置、缓存机制及请求次数，不能给固定倍数。用户与远端电脑时区不同，还可能继续答错日期。需要分别检查日期正确率、缓存读写、单任务成本和延迟，不能只看错误日志。

（c）宿主在每个新用户轮次自动生成日期、星期、IANA 时区和本周范围，放在已有历史之后的本轮输入中，稳定 system 内容不变。同一轮工具循环复用，新轮次和旧任务恢复后的新输入更新。时区优先用用户明确选择或偏好，再参考消息来源设备；不要直接使用远端执行机时区。排队、定时任务区分消息或触发时间与处理时间。精确时刻、跨午夜长任务再按需查询；本周新闻还要检索。用可控时钟验证跨年、跨时区、旧任务恢复等情况，并比较缓存、成本与延迟后逐步上线。

依据：docs/dev-rules/maker-core-and-agent-behavior.md §3.1–3.4；packages/maker-core/src/agents/claude-code/index.ts 的 system prompt 组装；agents/shared/usage-tracker.ts 的缓存统计。以上是设计方案，没有修改宿主代码或完成该方案的运行验收。

### A2 审阅 AI 排查报告

我不会直接启动一周重写。先请求客户端实际使用的生产接口，核对是否含新模型、响应版本与 schema：返回 45 条，先查发布、部署、响应版本或 CDN 等环节；返回 46 条，再核对客户端实际收到、解析、选择快照和界面过滤的结果。

服务端文件有 46 条、缓存有 45 条、updatedAt 相同，不能证明客户端收到过新版，更不能证明执行了报告所说的拒绝分支。整份快照未采用与单条模型不可见也不能混为一谈。同版本异内容可能违反不可变发布契约，客户端拒绝未必是缺陷。

报告还有两个过度结论：代码存在冲突告警，不能称为完全静默，但还要核对日志是否输出、运营能否看见；影响范围需按已有同版、较旧或无缓存及客户端版本分别复现，不能称所有用户。

实际比较还承担启动期与在线刷新保护、同版本冲突处理及 V5/V6 投影升级例外。深比较本身不会覆盖字段，也不能代替版本顺序；若逐字段混合新旧快照，才可能恢复旧的退休状态等字段。先定位，确认非法重发后提高 revision 向前修复，加发布 CI 断言和可见告警，再核验实际下发与 UI，不先删保护。

依据：packages/model-providers/src/modelRegistry.ts 的 compareModelRegistryRevisions；source.ts 的 selectNewerModelRegistry、preserveNewerCachedCatalog 与在线告警。此次为静态审阅，未取得题设故障的生产响应。

## Part B 动手做

### B1a 我的 PR 看板设计

1. 采用可关闭、重开的常驻面板。查看多条 PR、比较状态、刷新和选择分析对象，不应要求先启动 Agent；工具作为会话内按需查询入口。
2. 打开面板、刷新属于插件自主联网，需要声明 GitHub 域名并走宿主代理。在真实工具调用内携带 callId 的联网条件不同；宿主托管凭证及注入域名仍须声明，不能伪造调用来源。
3. 最小版本让用户通过宿主配置入口提供 PAT，由宿主凭证库保存和注入。插件只查询配置状态，不把明文放入聊天、KV、日志或源码。OAuth 需真实应用配置与用户授权，不能由 AI 代替批准。
4. 插件取数并结构化 PR、head SHA、失败 check/job/step、截断日志和链接，AI 解释原因并说明缺口。实际独立面板使用 cindy.tasks.create/send 创建可见任务；当前 Agent 查询工具则直接返回资料。受理不等于分析完成。

依据为插件作者手册 plugin-panels.md、plugin-network.md、plugin-agent-tasks.md；实际宿主接口核验记录见仓库 part-b/b1/validation/host-verification.md。

### B2 收工 Skill

（a）完整可执行文件为仓库 part-b/b2/end-of-work/SKILL.md。固定顺序：定范围 → 跑测试 → 完整审阅 → 扫描 → 摘要。定范围只读规则、测试入口与文件统计，不提前展开全部 diff；逐步记录实际结果，失败后继续能完成的检查。扫描核对已提交、暂存、未暂存及新增未跟踪来源，不把未改上下文计为命中；只报告，不自动清理或提交。

（b）固定流程、扫描边界、命令与退出码等记录字段，以及“结论、范围、改动、测试、审阅、扫描、待办”摘要模板。AI 判断具体测试范围、代码用途和失败原因；console.log 可能是合法 CLI 输出，不能机械删除。

（c）这是复用现有工具的会话工作流，不需独立面板或新增宿主能力，适合文本可审阅的 Skill。两轮共 8 个独立会话已实际执行：Codex CLI 与配置 DeepSeek 的 Claude Code；Pi、自动触发未测。仍有阶段记录晚写、完整审阅证据不足等偏差。Skill 能辅助收尾，不能保证严格一致；后续考虑用脚本核对事实记录，该改进尚未实现。

## 最后一题 我怎么用 AI

### a 笔试前的完整交付与分工

最近比较完整的一次是 RealRoute-Bench 的高德 API 数据采样。我说明采样目标、额度等约束和验收要求，AI 帮我规划额度、处理代理与网络、编写并执行采样程序，检查缺失、超时和数据完整性。我交付的是这部分采样流程和数据，不代表整个 benchmark 的基线与排行榜已完成。

使用 AI 时发现指令遗忘和过早声称完成的问题后，我又提出 Agent Replay 的思路、预期功能与设计约定，让 AI 辅助实现记录、回放和检查，另开审查 Agent 核对实现与测评。我还尝试过提供素材、视觉元素、转场和动态要求，让 AI 制作推广视频，再根据实际效果调整。

### b 那次有没有跑偏及如何发现

有，AI 有时漏掉前面的要求，或者只做了一部分就说完成。我会把原始要求与实际结果对照。采样不能只看程序跑完，还要核对请求记录、超时、缺失和检查结果。Agent Replay 的实现也要求审查 Agent 提供代码、日志或测试依据，不能因为换一个 AI 就直接信任。这里描述的是之前的项目经历，不拿本次 B2 测试代替。

### c 有没有写过规则

有，但没有系统地整理过，主要就是这些要求：

- 先勘察再下结论：优先确认真实代码入口、配置入口、测试入口和运行链路。
- 少说空话，避免把猜测包装成事实。
- 代码结论尽量附上入口文件、验证命令或关键路径。

加这些，是希望 AI 先看实际代码，再说明判断从哪里来，方便我核对，而不是没弄清项目就下结论。

### d 本套题的用量和控制方法

我粗估用了 ChatGPT Plus 当周额度的 30%，没有统一统计网页端、Codex 和 Cindy 的总 token 或总费用，不能把额度比例换算成金额。主要使用 GPT-6.1 Sol、medium；Cindy 参与插件制作；B2 实测使用 Codex CLI 和配置 DeepSeek 的 Claude Code，不代表验证了 Claude 模型。

我一般先规划方案，另开 AI 审查 raw 初稿，再修改自己的笔记。交付执行时尽量说清目标、目录、约束、产物和验收方式，只读相关入口。围绕报错和变化继续排查，不重复未受影响的检查；审查与验证也会增加消耗，我还需要改进什么时候值得多查一轮的判断。
