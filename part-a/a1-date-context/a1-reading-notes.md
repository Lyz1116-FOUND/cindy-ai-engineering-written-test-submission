# A1 日期参照问题的整理笔记

这份笔记合并“不同意.docx”和“不同意-最终提交版.docx”中的思考，记录保留的判断、需要修正的表述和静态核对依据。正式答案另存于 answers，原稿保持原样。

## 从用户问题开始

用户不想反复提醒日期，产品应自动提供准确的时间参照。我的原始判断是不同意立即把秒级时间戳放入 system prompt：稳定前缀可能被破坏，时区也没有定义。两份稿件保留了这个主线。

合并时以 a 判断、b 影响、c 方案组织正式答案，不将“AI 审核建议”附在正式答案末尾。个人设备时区与实际所在地不同的经历用于提示时区问题，不能据此证明模型一定会猜错所在地或触发额外检查；高德 API 的经历不作为 Cindy 当前行为的证据。

## 本次修正的判断

1. 题目已假设每次请求前更新时间，不能推导出日期必然停在启动当天。实际引擎的装配时机仍需核对，但不能用另一种实现替代题设。

2. 缓存变化从首次差异位置开始讨论。之前相同的部分仍可能命中；之后的计算可能不能复用。这里不涉及删除历史数据，也不能笼统地说缓存全部失效。

3. token 数量与计价类别分开。文本长度可能几乎不变，但缓存读取可能转为普通输入或缓存写入。价格和倍数取决于具体通道，原稿公式与固定增长结论不进入正式版。

4. 所有经过修改点且原本可受益于缓存的请求都可能受影响，不能只列不关机的桌面用户。语音、标题与 oneshot 是否受影响，需要共用注入点的证据。

5. 动态输入不等于不可复现。评测可注入固定时钟，记录时区与参照时间；问题是不能在未控制这些变量时直接比较快照。

6. 当轮输入的位置要看最终请求。新用户轮次追加日期可以尽量保留旧前缀；每个工具步骤都更新并修改原有时间块，仍可能扩大差异范围。不能无条件声称“新一轮本来就完全不命中缓存”。

7. 时间工具的结果也会进入上下文，可能成为后续请求的前缀；“工具调用不进前缀”不准确。工具适合按需取得新时间，不代表绕开缓存机制。get_current_time 在此是拟议名称，未核验为 Cindy 现有公共接口。

8. 服务端时间不天然正确，也不应给每次发送加一次网络校时。方案采用已校准的系统时钟，并可复用已有可靠校时结果；时区与绝对时刻分别处理。

## 我如何核对依据

先读两份 DOCX 的完整正文，再对照仓库行为规则，检查稳定前缀、热路径和 system prompt 改动要求。随后查看 Claude 适配器、usage 统计与调度时间上下文，确认规则在实际代码中对应什么入口。以上检索与静态核对由 AI 辅助完成。

docs/dev-rules/maker-core-and-agent-behavior.md §3.1：禁止向稳定前缀加入每轮变化的时间戳；§3.2：避免在发送热路径增加额外网络往返；§3.4：要求实测指标；§4：system prompt 改动需先由维护者确认。

packages/maker-core/src/agents/claude-code/index.ts：buildClaudeSystemPromptAppend 将 parts.userPrompt 纳入拼接，调用处再传入 systemPrompt。变量叫 userPrompt，不能证明它位于历史之后。

packages/maker-core/src/agents/shared/usage-tracker.ts：getCacheStats 按 turn 与 session 汇总缓存读写、未命中输入及命中率。冷启动或数据缺失不能代表长期命中率。

apps/desktop/src/main/scheduler-host/runner.ts：buildScheduledRunContextInstruction 传入 firedAtEpochMs、firedAtUtc 和调度时区时间，说明它们表示触发时间，而非排队后的处理时间。

## 我现在怎样理解方案

宿主生成可信的日期参照，随当前轮输入追加，保持已有历史和稳定前缀不变。普通交流使用日期、星期、时区和明确的周范围；精确时间按需查询。用户主动指定的历史日期和定时任务触发时间，不应被“最新日期优先”一律覆盖。

用户明确指定时区优先，再使用保存的偏好，随后参考发起设备；这是本方案的产品取舍，不是从当前代码核验出的统一优先级。跨设备需要实际检查时区信息怎样传递，不能只在本机拼字符串。

最新事实查询是另一条链：先把“这周”转成明确日期范围，再检索并核对事件发生时间。模型知道日期，并不会自动获得新知识。

## 实施前还需要验证什么

核对各引擎实际请求和旧前缀；用固定时钟检查跨日、跨年、跨时区、旧任务恢复、历史日期与排队。再对照日期回答、缓存、成本和首 token 延迟。以上是计划，尚未实测。
