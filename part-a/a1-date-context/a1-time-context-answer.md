# A1 日期参照问题的判断与方案

## a 我不同意直接上线这个方案

模型需要自动获得准确的日期参照，这应由产品保证。但我不同意把每次请求前生成的秒级时间戳放进稳定 system prompt 后立即上线。

首先，在按前缀匹配的缓存机制下，前缀相同才能复用。时间戳变化后，变化点之后的原有缓存可能无法复用；变化点之前的相同部分仍可能命中。失效的是计算缓存，历史消息并没有被删除。仓库的 maker-core-and-agent-behavior.md §3.1 明确禁止向稳定前缀加入每轮变化的时间戳。

其次，题目没有定义时区。用户、手机和远端执行电脑可能处于不同时区，直接使用执行机的本地时间仍可能答错日期。用户问“这周”，通常需要日期、星期、时区和明确的周范围，秒级精度没有必要。知道今天日期也不等于知道本周的新消息，最新事实仍需检索。

按题设每次请求前更新时间，可以改善部分日期回答，但没有解决缓存和时区问题。实施前还应核对各引擎真正发送的请求，确认时间的更新时机、位置和覆盖范围，不能只根据拼接代码判断可以上线。

## b 上线后的影响和发现方式

短对话中，模型可能开始答对日期，接口也不报错，普通功能测试容易通过。但经过这个修改点、原本能利用前缀缓存的请求，都可能受到影响。长上下文、多轮交流和多步 Agent 任务，可能损失更多可复用计算。是否影响语音润色、标题生成或 oneshot，要先确认它们是否共用修改点。

输入 token 数量不一定增加，但原本按缓存读取计费的部分，可能转为普通输入或缓存写入；在存在相应价差的通道上，成本会增加。首 token 延迟也可能上升。影响幅度取决于时间戳位置、其后的上下文长度、缓存机制与有效期，以及任务中的请求次数，不能脱离条件给固定倍数或“一周后变慢”的结论。跨时区用户还可能继续得到错误的日期解释。

这类回退可以被发现，但只看报错日志和几次短对话很容易漏掉。应在相同模型、相近上下文和工作负载下，对比缓存读取、缓存写入、未命中输入、单任务成本及首 token 延迟。日期回答正确与性能成本正常，需要分别验收。

## c 我的方案

1. 先定位错误来源。抽查实际送入模型的上下文，区分缺日期、日期过期、时区错误和旧任务恢复后仍用旧参照；同时区分日期理解错误与缺少最新事实。避免只修提示词，却漏掉时间来源或检索问题。

2. 宿主自动提供本轮日期。每个新用户轮次发送给 Agent 前，由宿主生成日期、星期、IANA 时区及按产品约定计算的本周范围。优先使用用户明确指定的时区，其次是用户保存的偏好，再参考发起消息设备的时区；缺失时明确默认值，不能让模型猜所在地，也不能直接采用远端执行机时区。例如，用户采用 Asia/Shanghai，日期参照为 2026-10-29 时，星期为周四；按周一至周日计算，本周为 10 月 26 日至 11 月 1 日。

3. 动态内容放进本轮输入。把宿主生成的时间参照放在已有历史之后，与当前输入一起交给模型，不逐轮改写前面的稳定 system prompt，不修改历史时间块。同一轮工具循环复用这份参照；新轮次、旧任务恢复后的新输入应重新生成。最终位置以各引擎实际请求为准，不能仅凭 userPrompt 等变量名判断。

4. 按需获取精确时刻。使用已校准的系统时钟；已有可靠的服务端校时结果可以复用，不为每次发送新增网络往返。普通日期问题不需要秒级刷新。问“还有多久”、长任务跨午夜或确需当前时刻时，再通过时间查询能力刷新；实施时核对已有接口，必要时提供 get_current_time 这类工具，工具定义保持稳定。

5. 保留不同时间的含义。排队消息区分消息时间与处理时间，定时任务区分触发时间与执行时间；“今天”按消息或任务原本的语境解释，不能一律用最新处理日期覆盖。不同任务的历史时间各有用途，不笼统地把所有日期都解释为最新一条时间块。若需补充固定的时间解释规则，应按仓库 §4 先与维护者确认，确认后保持文本稳定。

6. 验证后再扩大上线。用可控时钟验证跨零点、跨年、跨时区、旧任务恢复及用户明确讨论历史日期的情况，检查实际请求和代表性问题的回答。再以相同工作负载对比缓存与成本、首 token 延迟，先小范围上线，观察日期纠错反馈和性能指标，出现回退则停止扩大。用户问本周新消息时，先确定日期边界，再检索并核对事件发生时间；查询失败时明确未核验，不用训练记忆冒充最新事实。
